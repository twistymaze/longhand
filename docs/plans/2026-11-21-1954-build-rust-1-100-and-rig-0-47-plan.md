# Rust 1.100 and Rig 0.47 - Plan

## Goal Capsule

- **Objective:** Longhand builds on current Rig, so the summary agent work can use Rig 0.47 features, and users see no change in their summaries, model lists or stored files, except the Rig behaviour changes that R5 accepts.
- **Means:** One PR moves the Rust pin to 1.100.0 (KTD1) and `rig-core` to 0.47.0 (KTD2). It changes the summarize code for the new Rig API, and it keeps today's request bodies and file bytes (KTD3).
- **Authority:** This plan, then `CLAUDE.md` and `docs/development-workflow.md`. The R-IDs win on behaviour. The KTDs win on mechanism.
- **Execution profile:** One PR, title `build(deps): move to Rust 1.100.0 and rig-core 0.47.0`, which makes a patch release. Work in a new worktree from `origin/main`. Commit per unit.
- **Stop conditions:** Stop and report if `cargo deny check advisories` or OSV shows an advisory for rig-core 0.47.0 or rig-http 0.47.0. Also stop if the signed macOS release build fails on 1.100.0 in a way the PR #52 override does not fix, or if a Rig 0.47 change cannot keep a requirement below without new product behaviour.
- **Finish and ship:** `ce-work` implements, then opens the PR per [Before a PR](../development-workflow.md#before-a-pr), then runs `ce-babysit-pr` until the PR is ready to merge. After the merge, the summary-agent-foundation session rebases onto `main` and moves `rig-agent` to 0.47.0 itself.

## Product Contract

### Summary

Move the workspace to Rust 1.100.0 and `rig-core` 0.47.0 in one PR. Change the summarize crate for six API breaks in Rig 0.45–0.47, and keep JSON key order as it is today. Update the tests for four provider behaviour changes that Rig makes. Accept the Rig 0.47 version before the 7-day age limit only after a fresh advisory check.

### Problem Frame

The summary-agent-foundation branch (five unmerged commits) uses `rig-core` and `rig-agent` 0.44. Rig 0.45 and later have the agent features and fixes that the work needs, but they need Rust 1.97.1 or later, and Longhand pins 1.95.0. If the upgrade happens inside the agent branch, that PR changes the toolchain for the whole app as well as adding new features. A separate PR first keeps each change small enough to review and test alone, and gives the agent branch a stable base for its rebase.

The Rig changelog for 0.45–0.47 has many breaking entries. Most of them are in parts of Rig that Longhand does not use (harness, compaction, streaming, sign-in). Six change code that Longhand calls, and five change runtime behaviour on paths that Longhand uses. The full comparison, with file and line evidence for both versions, was made on 2026-11-21. Its findings are given in the KTDs and units below.

### Requirements

**Toolchain**

- R1. The workspace builds, lints and tests on Rust 1.100.0, in local checks and in each CI job.
- R2. Each place that names the Rust version names 1.100.0: the toolchain file, the workspace `rust-version`, the CI toolchain steps, `README.md` and `CLAUDE.md`.

**Rig**

- R3. `crates/summarize` uses `rig-core` 0.47.0, and no crate uses an older `rig-core`.
- R4. Summaries, model lists and context sizes work the same for each provider preset: the same fields and values go to the provider, in the same key order. The exceptions are the changes R5 accepts.
- R5. Four Rig behaviour changes go into the app on purpose, each one covered by a test:
  - The Gemini key goes in the `x-goog-api-key` header, not in the URL.
  - An error body with a numeric code inside a 2xx reply is handled as an HTTP error with that code, so a 429 starts the normal retry wait.
  - The reply allowance for a model comes from the refreshed Rig catalog, held to the model's context window.
  - For a Claude model that the Rig catalog marks as not reasoning, thinking level Off sends no `thinking` field. (session-settled: user-approved — chosen over sending `{"thinking":{"type":"disabled"}}` again: the field is for models that support thinking, and keeping it would override Rig's mapping.)
- R6. Files that Longhand writes from a JSON map keep the same bytes as today.

**Dependency rules**

- R7. rig-core 0.47.0 and rig-http 0.47.0 enter `Cargo.lock` before they are 7 days old only after `cargo deny check advisories` and OSV show no advisory for either crate. Each version has an entry in `min-age-exceptions.toml` with a reason.
- R8. The stored licence lists match the new dependencies.

### Key Decisions

- **A separate PR comes first, and the agent branch rebases after it merges.** (session-settled: user-directed — chosen over doing the upgrade inside the summary-agent branch, or after that branch merges: the agent work is not finished, so it changes code for the new API once, on a base that is already tested.) Governs R3.
- **Rig 0.47.0 skips the 7-day wait only after an advisory check.** (session-settled: user-directed — chosen over waiting until 2026-11-27: the agent work needs the new version now, and the check limits the risk.) Governs R7.
- **A change to what goes to a provider is a defect unless R5 accepts it.** The user confirmed this rule in the scoping synthesis. The four R5 changes are the Rig fixes that this upgrade is for. Governs R4, R5.

### Scope Boundaries

- No `rig-agent` change. It is not on `main`, and the summary-agent session adds it at 0.47.0 after its rebase.
- No new Rig features in the app, for example `ModelFacts`, streaming or the new `ProviderError::Stalled` handling.
- No change to Longhand's own retry rules. Rig 0.47 still does not retry a unary `Model::call`, so Longhand's retry rules stay in control.
- Considered and not built: a CI check that compares request bodies byte for byte across a dependency update. The provider body tests and the R6 file test find the one known cause (serde_json features). Build such a check if a second dependency changes key order.

#### Deferred to Follow-Up Work

- Remove the rig-core 0.47.0 and rig-http 0.47.0 entries from `min-age-exceptions.toml` on or after 2026-11-27, in a `chore` commit on `main`. The same commit removes the expired `rusqlite_migration` 2.7.0 entry (its reason says to remove it after 2026-11-17).
- The summary-agent-foundation session rebases, moves `rig-agent` to 0.47.0, and checks its plan's Rig 0.44 claims (KTD1, KTD4 of `docs/plans/2026-11-20-1211-chore-summary-agent-foundation-plan.md`) against 0.47.
- The old `rig-core 0.44` text in `docs/ideas/someday/apple-intelligence-provider.md` describes Rig at the time the idea was filed. Update it only when that idea moves.

## Planning Contract

### Key Technical Decisions

- KTD1. **Pin Rust 1.100.0, the latest stable, not 1.97.1, the minimum.** (session-settled: user-approved — chosen over 1.97.1: one toolchain change now instead of a second soon; the extra cost is more new lints in this PR.) 1.100.0 was released on 2026-11-09. Governs R1, R2.
- KTD2. **Pin `rig-core = "=0.47.0"`, an exact version, as today.** Rig makes breaking changes in each minor release, so an exact pin keeps `cargo update` from moving it. `default-features = false` stays. No feature that Longhand used was removed (`audio`, `image` and `websocket` were off). Governs R3.
- KTD3. **Turn on serde_json `preserve_order` in the workspace.** Rig 0.47 stops turning on `preserve_order` (rig PR #2934), and rig-core 0.44 was the only normal-build crate that turned it on. Without it, each `serde_json::Map` in the app uses sorted key order. That changes the key order of the request bodies that Rig builds, the bytes of `src-tauri/src/managers/local_store.rs` output, and the bytes of the `other` map in `crates/import-record/src/entry.rs`. #2934 names this line as the way to keep the old behaviour. The shared settings file sorts its keys itself (`crates/shared-settings/src/file.rs`), so it does not change either way. `float_roundtrip` was also dropped. Longhand sends no float that the change affects, so it stays off. Governs R4, R6.
- KTD4. **Read the reply allowance through `ModelSpec::output_limit()`.** `Catalog::find` is removed; `Catalog::get(provider, model)` returns a resolved entry, and accepts a dated snapshot of a listed id as `find` did. The refreshed catalog lists some OpenRouter output limits above the model's context window. `output_limit()` holds the limit to the window, which keeps a reply allowance from asking for more tokens than the model can hold. Governs R5.
- KTD5. **Accept the Gemini key header and the in-band error code.** Both are Rig fixes that providers expect. The header keeps the key out of URLs and logs. The status code lets Longhand's existing 429 rule apply to OpenRouter and llama.cpp replies that report a rate limit inside a 200 body. Longhand maps the error with its existing `http_error` path, and it adds no new rule. Governs R5.
- KTD6. **Pin `dtolnay/rust-toolchain` by full commit SHA at the action's `1.100.0` ref.** The repository setting rejects a `uses:` line without a full SHA. Resolve the SHA from the action repository's `1.100.0` ref, and keep the `# 1.100.0` comment. Governs R1, R2.

### Implementation constraints

- Read `docs/solutions/integration-issues/dependency-feature-changed-json-key-order.md` before U3, and `docs/solutions/build-errors/macos-27-rejects-stripped-release-proc-macros.md` before U6. Keep the PR #52 `[profile.release.build-override] strip = false` override. Its `retire_when` asks for a separate test before removal, and that is not part of this work.
- The Windows CI rust-cache key contains the toolchain-file hash, so the first Windows job after U1 runs cold. That is expected. The `windows-caches-follow-msvc-toolset` worktree edits other lines of `.github/workflows/ci.yml` and `.github/actions/windows-build-setup/action.yml`. Whichever PR merges second resolves the small conflict.
- New clippy lints on 1.100.0: fix the code. Add an `allow` only with a reason comment, and only when the lint is wrong for that code.

### Sequencing

U1 first, because Rig 0.47 does not build on 1.95.0. U2 needs U1. U3 and U4 need U2. U5 can run after U2. U6 runs last on the full change.

## Implementation Units

### U1. Move the toolchain to Rust 1.100.0

**Goal:** The workspace builds, lints and tests on 1.100.0 everywhere, with no code change in behaviour.

**Requirements:** R1, R2, KTD1, KTD6.

**Dependencies:** none.

**Files:**
- `rust-toolchain.toml`, `Cargo.toml` (`rust-version = "1.100"`)
- `.github/workflows/ci.yml` (four `dtolnay/rust-toolchain` steps), `.github/actions/windows-build-setup/action.yml` (one step)
- `README.md`, `CLAUDE.md`
- Source files that new 1.97–1.100 lints or warnings name

**Approach:**
1. Change the pin and the five CI steps (KTD6).
2. Run fmt, clippy for each target that CI lints (including the Windows lint that runs on macOS), and the workspace tests. Fix each new lint and warning.
3. Commit the lint fixes separately from the version change if they are large, so a reviewer can read the pin change alone.

**Execution note:** This unit is mostly configuration and lint fixes. A green full check is the proof, not new tests.

**Test scenarios:** Test expectation: none -- no behaviour change. The existing workspace tests are the check.

**Verification:** fmt, clippy and the workspace tests pass on 1.100.0. `rg 1\.95` outside `docs/plans/`, `docs/solutions/` frontmatter history and `docs/ideas/done/` finds no current version reference.

### U2. Change summarize for the Rig 0.47 API

**Goal:** `crates/summarize` compiles and passes its tests on `rig-core` 0.47.0.

**Requirements:** R3, R4, KTD2, KTD4.

**Dependencies:** U1.

**Files:**
- `crates/summarize/Cargo.toml`, `Cargo.lock`
- `crates/summarize/src/transport.rs` (both `HttpClientExt` impls, `TransportError::find`, `into_rig`)
- `crates/summarize/src/client.rs` (error mapping that matched `Error::Instance`)
- `crates/summarize/src/context.rs` (catalog lookup)
- `crates/summarize/tests/transport.rs`
- `crates/summarize/tests/providers.rs`, `crates/summarize/tests/models.rs`, `crates/summarize/tests/context.rs` (Gemini mock paths only)

**Approach:**
0. Before the lock file changes, query OSV and the RustSec advisory database for rig-core 0.47.0 and rig-http 0.47.0. If either has an advisory, stop (Goal Capsule, R7).
1. Before the version change, on rig-core 0.44, save the raw request body text of one summary request per provider preset (OpenAI Chat, Anthropic, Gemini, Ollama, llama.cpp, OpenRouter) as test fixtures. U3 compares 0.47 bodies with them.
2. `HttpClientExt` methods lose their type parameters. They take `Request<Bytes>` and return `LazyBody`, which holds `Bytes`. Change both impls and the test caller.
3. `Error::Instance` and `Error::instance` are removed. Make transport errors with `Error::transient` or `Error::permanent`, matching the kind of each error. Make `TransportError::find` match both variants, so the deadline, size-cap and redirect errors still reach Longhand's mapping.
4. Replace `Catalog::find` with `Catalog::get` and `output_limit()` (KTD4).
5. Remove `?key=` and `&key=` from the expected Gemini paths in the three test files, so the existing tests pass on 0.47. U4 adds the header assertions.

**Patterns to follow:** the existing transport and catalog code. Keep the start and end log lines, the deadlines, and the rule that no URL appears in an error.

**Test scenarios:**
- The existing transport tests (redirect refused, connect and total deadlines, reply size cap, no URL in an error text) pass after the rewrite.
- A transport timeout gives the same Longhand error kind as on 0.44, and the retry rule treats it the same.
- `catalog_output_max` for `claude-haiku-4-5` (64000) and `gemini-2.5-flash` (65536) is unchanged.
- A dated snapshot id of a listed model resolves to the listed model's limit, as with `find`.

**Verification:** `cargo test -p summarize` passes. `cargo tree -i rig-core` shows only 0.47.0.

### U3. Keep JSON key order

**Goal:** Request bodies and Longhand's JSON files keep today's key order (KTD3).

**Requirements:** R4, R6, KTD3.

**Dependencies:** U2.

**Files:**
- `Cargo.toml` (workspace `serde_json` features), member `Cargo.toml` files that need the workspace dependency
- `crates/summarize/tests/providers.rs`
- A test next to `src-tauri/src/managers/local_store.rs`

**Approach:**
1. Add `preserve_order` to the workspace `serde_json` dependency, so each crate that builds a `Map` gets it, whatever Rig turns on.
2. Confirm with `cargo tree -e features -i serde_json` that `preserve_order` is on in the normal build for each shipped target.

**Test scenarios:**
- For each provider preset, the raw body text of the summary request on 0.47 is byte-equal to the 0.44 fixture from U2. The Gemini key is not in the body, so the header move does not affect this test. If a preset's body differs in a way `preserve_order` does not fix, stop (Goal Capsule).
- The OpenAI Chat body test fails if `preserve_order` is removed.
- `local_store::write` with keys inserted out of order writes them in insertion order, byte for byte.
- `test_storage_folder` still passes (the settings file sorts its own keys).

**Verification:** both new tests fail with `preserve_order` off and pass with it on.

### U4. Test the accepted Rig behaviour changes

**Goal:** Each R5 change is in the app on purpose, with a test that shows it.

**Requirements:** R5, KTD4, KTD5.

**Dependencies:** U2.

**Files:**
- `crates/summarize/tests/providers.rs`, `crates/summarize/tests/models.rs`, `crates/summarize/tests/context.rs`
- `crates/summarize/src/client.rs` only if the in-band error mapping needs a change to keep Longhand's error kinds

**Approach:**
1. Gemini mocks: assert the `x-goog-api-key` header, and assert that no request URL holds the key. (U2 already changed the expected paths.)
2. Add a test for an in-band error body inside a 200 reply.
3. Add a test for an OpenRouter model whose catalog output limit is above its context window.

**Test scenarios:**
- A Gemini summary request has no key in its URL, and has the key in the `x-goog-api-key` header. The model-list and context requests do the same.
- A Gemini error text and log line contain no key.
- An OpenRouter 200 reply with `{"error":{"code":429,…}}` starts Longhand's 429 retry wait, then succeeds on the next attempt.
- A 200 reply with an in-band error code that is not 429 gives Longhand's HTTP error for that code, not "an empty reply".
- An Anthropic request for a Claude model that the catalog marks as not reasoning, with thinking level Off, has no `thinking` field. A reasoning Claude model with thinking Off still gets the same body as on 0.44.
- `catalog_output_max` for an OpenRouter model whose catalog output limit is above its context window returns the context window, not the listed output limit. (The reply allowance alone cannot show this, because `tokens::reply_allowance` already holds the ceiling below the context limit.)

**Verification:** `cargo test -p summarize` passes, and each scenario above has a test.

### U5. Advisory check, age exceptions and licences

**Goal:** The new versions meet the dependency rules.

**Requirements:** R7, R8.

**Dependencies:** U2 (the lock file has the new versions).

**Files:**
- `min-age-exceptions.toml`
- `licences/generated/*`

**Approach:**
1. Run `cargo deny check advisories` on the new lock file. U2 step 0 already checked the two Rig crates before they entered it. If an advisory shows, stop (Goal Capsule).
2. Add exceptions for rig-core 0.47.0 and rig-http 0.47.0, each with the reason "the summary agent work needs Rig 0.47; no advisory on 2026-11-21. Remove after 2026-11-27." The other new crates (httpdate 1.0.3, serde_path_to_error 0.1.20) are older than 7 days.
3. Run `scripts/check-licences.sh` and commit the files it writes.

**Test scenarios:** Test expectation: none -- dependency metadata only. The `cargo deny` CI job is the check.

**Verification:** `cargo deny check` passes, and the dependency-age check passes with the new entries.

### U6. Check the release builds

**Goal:** The shipped app still builds and runs on 1.100.0 on macOS and Windows.

**Requirements:** R1, R4.

**Dependencies:** U1–U5.

**Files:** none expected. If a build fails, the fix goes in the unit that caused it.

**Approach:**
1. Make a signed macOS release build per [Manual tests](../development-workflow.md#manual-tests). It shows that the PR #52 proc-macro override still works with 1.100.0 on macOS 27.
2. Make one summary with each hosted provider the user has keys for, and one with a local preset.
3. The Windows build and tests run in CI. Give Windows steps on nebula only if the user asks.

**Execution note:** Prefer a runtime smoke check over new unit tests here.

**Test scenarios:** Test expectation: none -- build and smoke check only.

**Verification:** The signed app starts, records a short note, and writes a summary. Windows CI is green.
